# Production Provisioning Runbook — VM156 (FW-004/FW-005, Future Work v2)

**Audience:** the AI agent executing the VM156 promotion, or a human operator.
**Scope:** converting VM156 from mock staging to a production-capable configuration: real-backend production config, production secrets, LDAP + emergency-local auth.
**Absolute rules:** no PDU actuation during any step; no production secrets in Git; VM154 remains production and untouched until the FW-011 gates pass and cutover is human-approved.

## 2. Provisioning sequence (mock → real, in order)

### 2.1 Verify staging baseline is healthy

```bash
ssh jordatech@10.0.20.156 'systemctl is-active pdu-control && \
  /opt/pdu-control/current/deploy/healthcheck.sh basic'
```

### 2.2 Provision production secrets (from VM154, out-of-Git)

Copy the production secrets file from VM154 to VM156 via the management workstation (no direct VM↔VM path assumed). Values transit the workstation in memory/pipe only; never write them to disk in the repo or print decoded values.

```bash
# On VM154 (read the file, stream base64 of the FILE — contents never displayed):
ssh jordatech@10.0.20.154 'sudo base64 -w0 /etc/pdu-control/secrets.env' > /tmp/pdu-secrets.b64

# On VM156 (decode in place with correct ownership):
ssh jordatech@10.0.20.156 'sudo tee /tmp/pdu-secrets.b64 >/dev/null' < /tmp/pdu-secrets.b64
ssh jordatech@10.0.20.156 'sudo bash -c "
  base64 -d /tmp/pdu-secrets.b64 > /etc/pdu-control/secrets.env &&
  chown root:pducontrol /etc/pdu-control/secrets.env &&
  chmod 640 /etc/pdu-control/secrets.env &&
  rm /tmp/pdu-secrets.b64 &&
  echo PROVISIONED (keys:) && grep -o \"^[A-Z_]*=\" /etc/pdu-control/secrets.env
"'
# Then shred the workstation-side temp copy:
shred -u /tmp/pdu-secrets.b64
```

### 2.3 Provision the Git-reconciled production config

```bash
# Ship the FW-001-reconciled config (authoritative labels) — via the release
# artifact's config example, applied as site config (allowed: this is the
# Git-managed mapping path, not an ad-hoc edit):
ssh jordatech@10.0.20.156 'sudo install -o root -g pducontrol -m 640 \
  /opt/pdu-control/current/config/examples/config.example.json \
  /etc/pdu-control/config.json'
```

> Note: `install.sh` never overwrites an existing config (REQ-015). This step is the ONE-TIME deliberate mapping reconciliation deployment (FW-001 acceptance), executed through the documented mechanism. Record it in the audit notes.

### 2.4 Switch backend to real (the FW-004 switch)

```bash
ssh jordatech@10.0.20.156 'sudo /opt/pdu-control/current/deploy/set-backend-mode.sh real'
# The script refuses to switch if secrets are missing or staging-throwaway.
```

### 2.5 Read-only real-backend validation (FW-011 subset — NO actuation)

```bash
# Login (emergency-local, LDAP separately) then:
# 1. UI outlet state display renders (GET / and /api/status)
# 2. outlet state reads return real ON/OFF from the PDUs
# 3. NO ON/OFF/REBOOT/CYCLE is sent — ever — during validation
ssh jordatech@10.0.20.156 'curl -sk -o /dev/null -w "%{http_code}\n" https://127.0.20.156/ ; true'
```

Automated read-only check (added in this sprint): `deploy/validate-read-only.sh` — logs in (emergency-local), GETs `/api/status` for all 3 PDUs, asserts HTTP 200 + parseable state, asserts zero POSTs. Detailed in its own header.

### 2.6 Record the provisioning in the handoff

Every step above and its output goes into the sprint handoff (§validation evidence).

## 3. Rollback (backend switch)

```bash
ssh jordatech@10.0.20.156 'sudo /opt/pdu-control/current/deploy/set-backend-mode.sh mock'
```

This restores the never-touches-hardware state without touching config/secrets.

## 4. What may NEVER happen

- Committing `secrets.env` contents (any variable, any encoding) to Git.
- Sending ON/OFF/REBOOT/Cycle Load to a physical outlet as a "validation".
- Editing production config ad-hoc on the VM (break-glass exception: Future Work v2 §12).
- Switching VM156 to `real` while staging secrets remain in place (script guards this).
- Powering off/rebooting VM154 or MIAM-00133 as part of provisioning.
